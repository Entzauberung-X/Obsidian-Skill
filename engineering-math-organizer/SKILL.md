## 数学笔记的本质：思维外化 · 活档案

> 工程数学笔记的价值 = 每个数学工具在工程里"用来解决什么问题"，**且记录"我如何理解这条 数学→工程 的路"**。思维外化 = 把"数学如何被理解、被误用、被落到工程"外化成可追溯、可迭代的认知档案——**写笔记 ≠ 搬运公式，写笔记 = 让"数学↔工程"的理解再发生一次。**

五条贯穿性原则（工程版，生成/深化每篇笔记时自检）：

1. **思维外化，非知识搬运**：公式/算法不只抄，要记录"为什么用它解决这个工程问题"（what + why + how）。
2. **顿悟必留痕**："原来这个公式在 XX 系统里是干这个的"是核心认知资产（`> [!note] 顿悟 ·「...」` 或思路轨迹笔记）。
3. **错题归因到思维漏洞**：从"工程误用/报错"反推"对数学的哪个理解有漏洞"，分类归因 + 对策 + 变式闭环。
4. **可追溯**：数学→应用 双向追溯 + 理解轨迹（原来以为 X → 现在知道 Y）。
5. **活档案·可迭代**：待补充落实删行回链；同类误用/顿悟沉淀 ≥3 条升级为专题。

> 📖 完整工程版哲学、两类新笔记模板（错题归因 / 思路轨迹，模块内相对编号）、多实现路径对比 → **`references/thinking-archive.md`**。创建这两类笔记前必须读它。

## 本质优先原则（从本质出发）

> 用户要求：**所有模块的所有章节（数学模块与应用模块），一律从数学本质出发组织**，而非从工程 / 算法 / 工具细节罗列开始。本原则对 001-009 与 101-105 全部笔记强制生效。

### 铁律

1. **先本质，后实现**：每篇笔记第一节必须先给出该主题的**数学本质**——它本质上是哪个数学问题（状态估计 / 概率推断 / 优化 / 几何 / 代数结构）。先写问题的数学形式（后验、MAP 目标、核心方程），再展开工程实现。
2. **一句话定位 = 数学 → 应用**：`[!abstract]` 必须写 `**{数学域}（工具）→ {应用}**`：{本质一句话}——先讲"用什么数学回答什么工程问题"。
3. **禁止以方法清单开头**：不得用"XX 算法 / XX 系统 / 工具对比"开篇。工程方法（特征法 vs 直接法、松耦合 vs 紧耦合、滤波 vs 平滑等）只能作为**本质问题的实例化**出现，而非内容主线。
4. **通用性优先**：能给出跨传感器 / 跨场景的通用本质就先给（如 SLAM = 轨迹×地图联合后验、控制 = 反馈稳定化、信号处理 = 表示与滤波），再落具体实例。
5. **公式先行**：核心数学结构（后验、目标函数、残差定义）在章节前部用 `$$\boxed{...}$$` 给出，作为全章骨架。
6. **工程落点必答（侧重工程）**：每篇笔记必须把该节数学工具映射到 1–2 个**具体工程场景**（从五大应用出口 101–105 中选，如"卡尔曼滤波更新步""波束形成 MVDR 加权"而非泛泛的"控制"）。**答不出工程落点的数学内容不属于工程数学笔记**——数学完备性服务于工程应用，不是目的。落点的具体形式见「工程落点（功能性识别）」。

### 反例 vs 正例

| ❌ 反面（从算法出发） | ✅ 正面（从本质出发） |
| :--- | :--- |
| "ORB-SLAM 用三线程实现 SLAM……" | "SLAM 本质是轨迹×地图的联合后验估计，ORB-SLAM 三线程只是对该后验的工程分解" |
| "特征法精度高、直接法速度快……" | "特征法与直接法是对同一观测模型 $h$ 的两种建模粒度" |
| "卡尔曼滤波分预测和更新两步……" | "卡尔曼滤波是线性高斯系统下贝叶斯后验的精确递推解" |

### 落地检查

- 核心笔记：§1 映射总表第一列必须是「数学域」；
- 子笔记：`[!abstract]` 按「数学 → 应用」模板；
- 每个正文章节内部：**先数学定义，后工程落点**。

## 工程落点（功能性识别）

> 每个数学概念都必须"落到工程"。判断标准是**功能**而非单一格式：凡是将该数学工具映射到**具体工程场景**（点名算法/系统，而非泛泛"用于控制"）的形式，都算合格。

### 可接受形式清单（满足任一种即合格）

1. **专属工程应用子笔记**：`07、工程应用.md`（005/007/008/009 已有先例），以"数学工具 → 工程出口 → 应用场景"表收束全模块。
2. **章节内 `## 工程应用`**：子笔记末尾独立章节，逐条映射到具体算法/系统（如 `002、线性代数/05、二次型与正定性` §7）。
3. **工程类 callout**：`> [!tip] 工程捷径 / 工程要点 / 工程意义 / 工程价值 / 工程直觉` 等，内容点名算法/系统。
4. **映射表含工程列**：表格含「工程出口 / 应用场景 / 工程落点」列（如 `008、李群流形与旋转数学/07、工程应用` 的"数学工具|工程出口|应用场景"）。
5. **`> [!example] 工程落点`**：若使用该显式 callout 亦合格（格式见下，非强制）。

显式 callout 格式（可选）：
```markdown
> [!example] 工程落点
> {具体工程场景（点名算法/系统）}：{该数学工具在那里扮演的角色}
```

### 编写要求

- 每篇笔记至少 1 处工程落点；**宁可具体**（点名算法/系统）也不泛泛（"用于控制"）。
- 数学模块笔记（001-009）优先映射到已有应用子笔记（101-105），并回链。
- 应用模块笔记（101-105）反向标注其数学依赖（001-009），形成双向链。
- 深化数学概念时若找不到真实工程出口，在对应核心笔记 `## 待补充` 记一条"待找工程应用"，不强行编造。

## 理解注释（概念直观解释）

> 给子笔记 / 核心笔记中的关键概念添加「为什么」的直观注释——让读者不仅看懂公式，更懂本质。与「本质优先原则」配套：先用数学本质立骨，再用一句话直觉把它"钉"进脑子。

**格式**：

```markdown
> [!note] 理解 ·「口诀名」
> {直观解释：本质 / 为什么 + 几何或类比直觉 + 操作提示}
```

**放置**：每个概念子节（`### 1.1` 等）的公式块之后、下一个子节之前；若该节已有 `[!tip]` / `[!success]` / `[!warning]` 等 callout，注释放在它们**前面**（先本质，后操作）。

**编写原则**：
- 每个独立概念 **1 条**、**2–4 行**，30 秒可扫读
- 讲「为什么」与直觉（几何图景 / 类比 / 与上游数学的关联），**不重复公式本身**
- 与既有 callout 互补：已有 `[!tip]` 讲"怎么操作"，理解注释讲"本质是什么"
- **不新增公式 / 结论**，只解释既有内容；不修改原文公式、表格、标题
- 某概念已有等效理解（如既有 `[!note]` 已讲清本质）时，只补缺失的角度，不重复

**落地检查**：每条注释落在对应概念子节内；全笔记无孤立注释（脱离上下文的"名言警句"）；结构完好（frontmatter / `---` / 表格未破坏）。

## 待补充记录机制

> 用户要求：**记录笔记可待补充的内容，后续已补充删去记录。**

- **范围**：模块核心笔记 + 工程数学总览末尾各带一个 `## 待补充` 节。
- **格式**：`- [ ] {待补充内容}`（checkbox）
- **规则**：
  - 新增待补充项：当某个方向"未来可能深挖但当前未写"时，追加一条 `- [ ]`。
  - **已补充删去**：当某待补充项被展开成笔记后，**必须**从原列表删去该行（同步在核心笔记导航/学习路径加入新子笔记链接）。
  - 深化一个方向后，记得回到对应核心笔记 + 总览，删除已完成的待补充项。
- **待补充 vs 子笔记**：待补充是"想法清单"；一旦落实为子笔记，就从未完成态转为已完成，删去记录。
- **迭代升级（活档案）**：同类误用/顿悟沉淀 ≥3 条 → 升级为专题或并入相关应用模块子笔记；删待补充行、回链。

### 死链检测脚本（修正版）

> 从 **vault 根目录**运行（不是 `数学/工程数学`）。处理：full-path 链接、模块内短名、跨库链接、`\|` 转义管道、含空格路径。

```bash
cd "C:/Users/gk20230929/Documents/Obsidian Vault"   # vault 根目录
grep -rhoE '\[\[[^]]+\]\]' --include="*.md" "数学/工程数学" \
  | sed 's/\[\[//; s/\]\]//; s/|.*//; s/#.*//; s/\\$//' \
  | sort -u \
  | while IFS= read -r l; do
      [ -z "$l" ] && continue
      if [[ "$l" == */* ]]; then
        [ -f "$l.md" ] || [ -f "数学/工程数学/$l.md" ] || echo "DEAD: $l"

      fi
    done
```

## 核心工作流

### 工作流 1：新建模块
1. 确认模块类型：数学（`0XX、`，下一可用编号 001-009）或应用（`1XX、`，下一可用编号 101-105）
2. 新建目录 + 核心笔记（按核心模板）
3. 更新 `000、工程数学总览.md`：导航表行 + Mermaid 节点 + 交叉知识点 + 关联笔记
4. 在核心笔记 `## 待补充` 中列出未来子笔记方向

### 工作流 2：展开子笔记 / 深化专题
1. 从核心笔记 `## 待补充`（或用户指定）选题
2. 按子笔记模板创建（150-220 行、boxed 公式、表格、工程落点）；**第一节先写数学本质**，按「本质优先原则」
3. 按「链接规范」互链：模块内短名、跨模块 full-path，≥2 交叉引用
4. 更新核心笔记「本模块展开笔记」+ 学习路径
5. **在核心笔记 `## 待补充` 中删去已完成的项**
6. 并行创建时：给各 agent 完整模块文件清单，保证交叉链接最终可解析

### 工作流 3：健康检查
按上方清单执行；死链/编号错误/考研引用任一不过 = 不合格。

### 工作流 4：概念理解注释增强

**触发**：用户要求"给概念添加理解注释"、"给概念加注释 / 解释"、"XX 概念怎么理解"、"优化 XX 笔记的理解"

**操作**：
1. Read 目标笔记，列出全部概念子节（`### x.y`）
2. 对每个独立概念写 1 条 `> [!note] 理解 ·「口诀名」`，严格遵循「理解注释」规范
3. 既有 callout / 公式 / 表格 / 标题 / 关联笔记一律不动，**只增补**
4. 完成后自查：每个概念子节有且仅有一条注释；未引入新公式；frontmatter 与 `---` 结构完好

### 工作流 5：工程应用补全（侧重工程）

深化一个数学概念（001-009）时，主动为其找工程出口：
1. 在 101-105 应用模块中搜索该数学工具的实际用法（按关键词 grep）
2. 找到：在数学笔记加工程落点（按「工程落点（功能性识别）」任意形式）并链到对应应用子笔记
3. 找不到：在对应模块核心笔记 `## 待补充` 记一条"待找工程应用"，不强行编造
4. 反向：深化应用模块概念（101-105）时，标注其数学依赖（001-009）并回链数学笔记

**触发**：用户要求"记一次工程报错/误用""这个数学在 XX 里是干这个的""XX 我总算想通了"。
